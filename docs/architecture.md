# Architecture

How Preston is put together. Product intent lives in the [spec](../specs/20261116-preston-first-release/spec.md), terms in [CONTEXT.md](../CONTEXT.md), and binding decisions in [docs/adr](adr/). Keep this file current when a boundary or contract changes.

## Processes

`preston` is the only user-facing command. One executable (`dist/cli.js`) serves three roles:

| Invocation | Role |
|---|---|
| `preston` | Registers the daemon to start at login (see Login service), ensures the daemon is running (starting it detached if needed), runs the deterministic agent-choice step if no agent is configured, then opens the terminal Channel: a conversation with the Coordinator. Ctrl+C leaves the conversation; the daemon keeps running. |
| `preston daemon` (internal) | The long-lived runtime. Owns all state, timers, Channels, and agent processes. |
| `preston mcp --token <t>` (internal) | A stdio MCP server that an agent CLI launches. It proxies Preston's tools to the daemon over IPC. The token identifies the caller's role (Coordinator or Worker) and its Run. |

The daemon and its clients talk over a local IPC endpoint: a Unix domain socket at `<home>/preston.sock` (in the temp directory if that path would be too long), or a named pipe on Windows. Messages are newline-delimited JSON-RPC 2.0. Every connection must first call `auth` with the secret in `<home>/ipc-token`, which is readable only by the owner. A lock file (`<home>/daemon.lock`) keeps one daemon per home, so the login service and `preston` can both start it safely: the loser exits with status 0. A lock whose process is gone is taken over, and so is one whose process has not answered on the endpoint within 20 seconds of taking the lock.

IPC methods: `health`, `shutdown`, `terminal.attach` / `terminal.send` (replies arrive as `terminal.message` notifications), `setup.state` / `setup.chooseAgents` / `setup.continue`, and `mcp.describe` / `mcp.call` for the MCP proxy.

`preston --version` prints the version for diagnostics. Like the internal roles it is undocumented for users; it is not a command. The executable drops Node 22's one-off `node:sqlite` ExperimentalWarning and leaves every other warning alone.

## Login service

`src/service` registers the daemon with the OS service manager, per user and without administrator rights. It runs the same Node (`process.execPath`) and real `dist/cli.js` path the user ran, with `PRESTON_HOME` set (on Windows only for a non-default home, which the launcher sets); stdout and stderr go to `<home>/logs/daemon.out`. The default home uses the names below; any other home gets the same names with a hash suffix, so homes never overwrite each other.

| OS | Registration | Fallback |
|---|---|---|
| macOS | LaunchAgent `~/Library/LaunchAgents/ai.polyweave.preston.plist`, loaded with `launchctl enable` + `bootstrap gui/<uid>`. Restarted only on a crash (`KeepAlive.SuccessfulExit = false`). | If loading fails (no GUI session), the plist still starts it at the next login. |
| Linux | systemd user unit `$XDG_CONFIG_HOME/systemd/user/preston.service`, `daemon-reload` + `enable --now`, `Restart=on-failure`. | Without a user manager: XDG autostart entry on a graphical session; otherwise not registered, and the user is told. |
| Windows | Scheduled task `Preston`, created from XML with a logon trigger and principal scoped to the current user and `LeastPrivilege` (`/SC ONLOGON` would mean any user, which needs administrator rights). It runs `wscript.exe` on `<home>/service/start-preston.js`, which starts Node with no console window. | `Preston.cmd` in the user's Startup folder, if task creation is refused. |

macOS and Linux services get the user's `PATH` with Node's directory first, because the agent CLIs need `node` and service managers start with a minimal `PATH`. `<home>/service.json` records what was registered (definition version, Node path, entrypoint, home). When that is unchanged and the artifact still exists, nothing is touched; otherwise it is re-registered, which covers Node moving after an nvm, Volta or fnm upgrade. `PATH` is deliberately not part of that record, so different shells don't cause re-registration.

Registration never fails `preston`: an error becomes one plain notice ("Preston is running now, but it won't start by itself…"), shown once until it changes. `removeStartAtLogin` undoes everything for a future uninstall; it is not a user command. All OS access goes through an injectable command runner and file system (`ServiceHost`), so tests assert the generated files and commands for every OS on any host.

## Data

`<home>` is `$PRESTON_HOME` if set, otherwise `~/.preston` on every OS. It holds:

- `config.json`: typed, validated config, plain text, mode 0600 (see the Secrets section of the spec). Every change is also recorded as a version in the database so it can be rolled back.
- `channels/<kind>.json`: state a chat Channel updates by itself (WeChat's long-poll cursor and context tokens), mode 0600. It is kept out of `config.json` so frequent updates do not become config versions and a rollback never rewinds it.
- `preston.db`: SQLite via `node:sqlite`, with no native dependency. It holds Goals, Briefs, Runs, Sessions, events, questions, escalated approvals, quota state, the outbox, config versions, standing order versions, schedules with their run keys, and the memory search index.
- `memory/`: what Preston knows about the user, as Markdown (`USER.md`, and `projects/<name>-<hash>.md` per Project). These files are the source of truth; the database only indexes them. See Standing orders, schedules and memory. Migrations are forward-only and numbered.
- `logs/` and `transcripts/`: `logs/preston.log` is structured JSON lines with secrets masked, and `logs/daemon.out` is the daemon's stdout and stderr; `transcripts/<runId>/` holds agent transcripts and check output, referenced from the database by path.
- `coordinator/`: the working directory of the Coordinator's agent Session.
- `worktrees/<project-slug>/<goal-id>`: one git worktree per coding Goal (see Projects, worktrees and landing); removed when the work lands or, for Goals that did not land, by the tidy-up described there.
- `service.json`: what the login service registration last recorded; `service/` holds the Windows launcher and task XML.

Nothing Preston owns is ever written inside a Project. The one unavoidable exception is Git's own bookkeeping: a worktree and its `preston/<goal-id>-<slug>` branch are recorded in the repository's `.git`, and removed again when the work lands (or, for work that did not land, the worktree after a retention period; the branch is kept).

## Runtime components (inside the daemon)

```text
 Channels ──inbound──▶ Router ──fixed words──▶ deterministic replies
   ▲                     │
   │                     └─▶ Coordinator (agent Session + coordinator MCP tools)
 Outbox ◀── notifications ◀──┐            │ goal_create / ask_human / config_* …
                             │            ▼
                         Goal engine ──▶ Worker adapters ──▶ claude / codex / fake
                             │  ▲             │ WorkerEvents
                             ▼  └─────────────┘
          Supervisor (timers, stalls, quota monitors, recovery)   Store (SQLite)
```

- **Channels** connect to the outside world and normalise messages. The owner check happens in the Channel, based on its pairing. The terminal is always registered; Discord, Slack and WeChat are built from `config.channels` (`src/channels/chat.ts`) and rebuilt when their section changes (config_update, rollback, channel_configure). Changes a Channel makes itself (a pairing result, a cursor) are saved without rebuilding it. `ctx.notifyHost` goes to a `HostNotifier` (`RuntimeOptions.notifyHost`); without one it is only logged.
- **Router** handles fixed words (`status`, `stop`, `pause`, `resume`) without calling a model, and serialises everything else into Coordinator invocations. `status` starts with a plain line for any agent that cannot work ("Codex is out of quota until 3:40pm. 2 Goals running, 1 waiting for quota."); `resume` also rechecks spending limits and logins at once. While a Channel's pairing waits for an answer in a conversation (WeChat's phone number), the owner's next message there goes to the pairing instead; it is never written to the inbox or queued for the Coordinator.
- **Coordinator** is an agent Session (Claude or Codex, through the same adapters as Workers) whose tools are Preston's coordinator MCP tools. Each invocation resumes the persistent Coordinator Session with a new input, such as a user message or a meaningful event. The text of its final reply is sent back to the originating Channel. Its model and effort default to Sonnet 5.5 (`claude-sonnet-5-5`; the `sonnet` alias on Bedrock, Vertex or Foundry) or GPT-6.1 Sol (`gpt-6.1-sol`), Medium; a model the account does not offer (Codex `model/list`) falls back to the user's own default with a note shown in `agents_status`.
  - Owner messages are written to the durable inbox (`inbound_messages`, deduplicated by Channel and native ref) before the Coordinator sees them, and marked handled in the same write that records the reply. A message whose turn was cut off by a crash or shutdown is replayed once on the next start, with a note to check what was already done; `goal_create` is idempotent per message.
  - When the Coordinator's agent is out of quota or signed out, messages stay in the inbox and get one deterministic "queued" reply each, without a model call. They are answered in order when that agent's bucket recovers, or straight away by another enabled agent with headroom when `agents.balanceByQuota` allows it. Worker questions go straight to the user meanwhile.
- **Goal engine** is the durable state machine for Goals and Runs. It starts Runs, consumes WorkerEvents, handles `ask_preston` and `report_result`, runs verification, and emits notifications.
- **Supervisor** holds the deterministic timers: stall detection, quota rechecks and recovery on startup. Schedules have their own dispatcher (see below). It never calls a model directly; it raises events to the Coordinator only when judgement is needed. See [Supervision, quota and recovery](#supervision-quota-and-recovery).
- **Host notifier** (`src/notify`) backs `ChannelContext.notifyHost`, for example when WeChat ends Preston's login: `osascript` on macOS, `notify-send` on Linux if installed, a PowerShell WinRT toast on Windows with `msg` as a last resort. The text is always a separate argument or environment variable, never part of a shell command or script. The same text is shown at most once an hour and at most three notifications every ten minutes. It never throws. Only the daemon process enables it; `createRuntime` alone just logs.
- **Outbox** delivers every outgoing message durably, retries, and records delivery state. A delivery failure never fails a Goal. Items are attempted only while their Channel is connected, in order per Channel, with exponential backoff; dedupe keys make acknowledgements, questions and outcomes go out once, even across restarts. Routing: replies and the Goal acknowledgement go to the originating conversation; questions and final outcomes go to every registered Channel. When a question is answered, undelivered copies are withdrawn and delivered copies on Channels with reactions are marked answered; nothing else is sent.

All time-dependent logic takes an injectable clock, so tests can control time.

## Contracts

These are the seams. Tests drive Preston through them, with fake Channels and fake Workers.

- **Channel**: `start(ctx)`, `stop()`, `send(message) → delivery result`, optional `markAnswered(messageRef)`, and `capabilities` (reactions, proactive delivery). It reports inbound messages through `ctx.onMessage`.
- **WorkerAdapter**:
  - `detect()` reports whether the CLI is installed, its version and its login state.
  - `startRun(...)` starts a Run, or resumes one when given a native Session ID. Inputs: workdir, prompt, optional model/effort, and the MCP launch spec. It returns a handle with an async stream of `WorkerEvent`s, the native Session ID, `interrupt()`, and optionally `processId()` (the agent process, recorded for orphan cleanup).
  - Optional `readQuota()`.
  - Native approval requests are answered by Preston's approval policy ([ADR 0003](adr/0003-preston-answers-native-approval-requests.md)).
  - Every process the built-in adapters start gets the daemon's environment without a parent agent session's variables (`src/workers/env.ts`: `CLAUDECODE`, Claude Code session, host and SDK plumbing, Codex thread, sandbox and shell-snapshot variables). The user's own configuration and credentials are kept.
- **WorkerEvent** kinds: `started`, `activity` (including whether a tool or command is still running), `message`, `quota_blocked` (bucket, kind, reset time if known), `auth_error`, `completed` (final text and usage), `failed`, `exited`.
- **Adapter and Channel registration**: `src/workers/registry.ts` (`builtinAdapters()` / `BUILTIN_ADAPTERS`: the Claude Code and Codex adapters, factories receiving `AdapterContext`) and `src/channels/registry.ts` (`CHAT_CHANNELS`: per kind, a settings schema, the credentials the user pastes, the keys kept as Channel state, the setup guide, and a factory receiving the settings and a `persist` callback). The terminal Channel is always registered. When the test-only `PRESTON_TEST_FAKE_AGENT` names a scenario module, the daemon uses only the fake adapter.
- **PairingIO**: `show(text)`, optional `prompt(question, { secret })`, `signal`. Pairing runs in the background (`src/setup/pairing.ts`): `show` and `prompt` talk to the conversation that asked for it, the outcome's `configPatch` is saved, and the Coordinator gets a setup event.
- **MCP tools**: owned by the daemon. `preston mcp` asks the daemon which tools its token may see and forwards calls; it holds no logic. Tokens are minted per agent turn, kept in memory, and revoked when the turn ends, so a daemon restart invalidates all of them. Coordinator invocations use `StartRunInput.runId = "coordinator"`. Claude's permission prompt tool is `mcp__preston__approve`.
  - Coordinator role: Goals, briefs, answering Workers, `ask_human`, `approval_decide`, config get/update/history/rollback, status, setup (`agents_status`, `channel_status`, `channel_setup_guide`, `channel_configure`, `channel_pair`, `channel_remove`), standing orders, schedules and memory (see below). `config_update` checks a change before saving it: newly enabled agents must be installed, models and efforts must be offered (Codex lists them; Claude names and efforts are checked by shape; a Worker model must work for every enabled agent), and Channel settings must be valid. A refused change leaves the config as it was. Tokens given to `channel_configure` are masked in results and logs.
  - Worker role: `ask_preston` and `report_result` (summary, checks performed, suggested verification commands, blockers).

## Standing orders, schedules and memory

The runtime owns persistence and timing. The Coordinator only turns what the user says into tool calls, and those tools change durable state only while it is answering an owner message (`src/mcp/owner-turn.ts`); a Worker question, a repository file or a non-owner can never write one. All three are changed in chat and none of them runs a model by itself.

| | Goal | Standing order | Schedule | Memory |
|---|---|---|---|---|
| Is | one finite outcome | persistent rule about how Preston works | deterministic trigger | durable fact or preference about the user |
| Code | `src/goals` | `src/standing` | `src/schedule` | `src/memory` |
| Tools | `goal_*` | `standing_order_create / update / list / disable / history / rollback` | `schedule_create / update / list / pause / resume / delete / history / run_now` | `memory_search / upsert / remove` |

**Standing orders** are small records `{scope, authority, trigger, constraints, escalation, policy}`, stored as numbered versions in `standing_order_versions` (history and rollback, as for config; a rollback is a new version). Five global defaults are seeded once (own the objective, recover from routine obstacles, escalate only what needs the user, verify with evidence, communicate briefly); they are ordinary orders and can be edited or disabled, and a disabled default is not seeded again. Scope is `global`, `project:<folder>` (everything inside it) or `schedule:<id>`; trigger is `always`, `goal`, `schedule` or `message`, optionally narrowed by keywords. Applicable orders are chosen by deterministic matching, never by a model, rendered compactly (most specific kept first, capped by `standing.tokenBudget`, about four characters a token, with a note when some were left out), and appended to a Worker's system guidance (`EngineDeps.workerContext`) and to the Coordinator's system prompt (`CoordinatorDeps.contextBlocks`). Text containing a credential is refused. Orders also carry typed policy flags that other modules read through `StandingOrders.effectivePolicy({ projectPath?, scheduleId? })`; the most specific enabled order that sets a flag wins, and unset flags take their default. The set is deliberately tiny: `landing.autoMergePublishing` (default false), which lifts the question before a merge that would publish. Add a flag only together with its consumer and its default.

**Schedules** (`src/schedule`) are `{trigger, timezone, job, project, overlap, missedRun, delivery}` with `nextRun` persisted. A trigger is one time, a cron expression (five fields, evaluated in the schedule's IANA time zone) or an interval. `cron.ts` is a small dependency-free implementation: a wall time inside a spring-forward gap runs once when the clocks jump, a wall time that happens twice runs once (the first), except that hourly (`*` hour) jobs keep running each real hour. The dispatcher is one timer on the injectable clock, never longer than `schedules.tickMs`, so waking from sleep is noticed within a tick. Each due time is claimed under a durable run key (`schedule_runs` unique on schedule and scheduled time, plus the Goal's `sourceKey`) in the same transaction that moves `nextRun`, so a restart cannot dispatch it twice. A host that is asleep or off cannot run anything: on the first tick after Preston runs again, due times are handled per `missedRun`: `catch_up` (default) runs the latest missed time once if it was due within `schedules.catchUpWindowMs`, otherwise (and for `skip`) it is recorded as skipped. `overlap` is `skip` (default) or `queue` (at most one waiting run, started after the previous Goal ends). A job is either a Goal template (Brief), started through `GoalEngine.createGoal` as a distinct Goal with no acknowledgement, or a script check (command and expected exit code, no model) that only starts a Goal, or notifies, when it fails. A run is linked to its Goal and settles with the Goal's outcome; the user is told through the normal outcome message, plus one notice when a missed run is caught up, a job cannot start or a check fails. Pausing does not catch up the paused time.

**Memory** (`src/memory`) holds global and per-Project facts as one line each in Markdown, with provenance (source, channel, version, timestamps) in a trailing comment; lines typed by hand are adopted. Writes take an in-process queue plus a lock file, re-read the file, and replace it by writing a temporary file and renaming it, so concurrent writers cannot clobber each other. Entries are deduplicated by normalised text and by key. Text that looks like a credential, or equals a secret Preston knows, is refused. `memory_docs` indexes memory and a summary of each finished Goal (objective, outcome, Worker summary, project, links to its transcripts), added lazily and idempotently when memory is searched or Preston starts; it is searched with SQLite FTS5 (`unicode61`, with CJK split per character so Chinese text is searchable) or, where FTS5 is missing, substring matching. The Coordinator's system prompt gets a "what you know about the user" block of global facts only, with no timestamps, so the text is identical until memory changes (prompt caching), capped by `memory.contextChars` (newest kept). Workers keep their own AGENTS.md or CLAUDE.md; Preston does not copy those.

## Goal lifecycle

States: `queued → running → verifying → completed`. Side states are `waiting_for_quota`, `waiting_for_login`, `waiting_for_user`, `recovering`, `paused`, `blocked`, `failed` and `cancelled`; `completed`, `blocked`, `failed` and `cancelled` are terminal. A completed Goal carries an outcome of `verified` or `unverified`. A Run is `active` (a turn is executing), `parked` (between turns, waiting for an answer, quota or resume) or `ended`; one Run can span several turns of the same native Session.

- The worker exiting is never success. A turn that ends without `completed` is recovered (resume the Session with a recovery note, or restart from the Brief without one), up to `recovery.maxAttempts`, then the Goal fails.
- After `report_result` and a completed turn, Preston runs the Brief's checks plus Worker-suggested commands that the approval policy classes as routine. "Verified" needs at least one Brief check and every check passing; suggested commands alone give "Unverified". Failing checks resume the Worker with the evidence up to `verification.maxFixAttempts` times. Reported blockers end the Goal as Blocked.
- `ask_preston` waits up to `questions.workerWaitMs` for the Coordinator, otherwise (or once escalated to the user) it tells the Worker to finish independent work and end its turn. The answer resumes the same Session.
- On startup, every non-terminal Goal is reconciled against reality before anything resumes: orphaned agent processes are terminated, running Runs are recovered, verification is re-run, pending Coordinator questions, approvals and decisions are raised again, quota monitors resume from their persisted schedule, and unhandled inbox messages are replayed.
- Every Goal records the tactics tried on it (`attempts`: stall resume, strategy events and decisions, agent handovers), so Preston changes strategy instead of repeating one.
- An approval the policy escalates becomes an `approvals` row linked to a Worker question, and a Coordinator event. The Coordinator decides it with `approval_decide` within the Brief's authority, or asks the user with `ask_human`; once the question is with the user, only an owner message can decide it. The Worker's native request (Claude's permission tool call, Codex's approval request) waits up to `approvals.escalationWaitMs` (2 minutes). A decision in time is the native answer. Otherwise the request is declined with a note that it was escalated; the Worker carries on and ends its turn, the Run parks as `waiting_for_user`, and the later decision resumes the same Session through the parked-question path. Undecided approvals are raised again after a restart.

## Projects, worktrees and landing

All of this lives in `src/landing`. The Goal engine sees it only through `LandingHooks` (`src/landing/hooks.ts`): `prepare` before every turn, `land` after verification, and a few queries used by recovery. Git is always run as `git` with an argument array in an explicit working folder (never a shell string), with `GIT_DIR`-style variables removed, so it behaves the same on Windows, macOS and Linux. GitHub is reached through the `GitHubClient` interface; the real one drives `gh`, and tests inject a fake backed by a real bare repository.

**Projects.** A Project is a folder identified by its canonical path (symlinks resolved, Windows case normalised), created by `goal_create` and listed by `project_list`. Each Goal start re-inspects it read-only (`src/landing/project.ts`): is it a repository (and is the folder a subfolder of one), bare, without commits, on a detached HEAD, does it use submodules, what is the main branch (the remote's default, `init.defaultBranch`, then `main`, `master`, `trunk`, `develop`, the checked-out branch), which remote, and does it have uncommitted edits.

**Isolation.** A Goal in a repository works in `<home>/worktrees/<project-slug>/<goal-id>` on branch `preston/<goal-id>-<slug>`, created at the tip of the main branch (or of the checked-out branch when the Brief says `workspace.startFrom: "current"`). `prepare` is idempotent and records the worktree in `goal_workspaces`, so after a restart the same folder is reused, and a folder that went missing is re-attached to its branch. The user's own checkout, branch and uncommitted edits are never touched. A non-repository folder works in place. When a worktree cannot be made (no commits, no usable base branch, submodules that will not initialise, Windows path length, a git error) the Goal is Blocked with a plain explanation, unless the Brief sets `workspace.allowInPlace`, in which case the Worker works in the folder and the outcome says so. A bare repository is always Blocked. Worktree creation is serialised per repository.

**Landing.** After the Brief's checks pass (Verified), the engine calls `land`. It is a sequence of steps that each look at what exists before acting and are recorded in `landings` / `landing_ops`, so a crash resumes instead of repeating:

1. Commit whatever the Worker left uncommitted on the Goal's branch (message from the Brief, no trailers; a failing commit hook goes back to the Worker). Changes to files Git already tracks are always committed. New files follow the project's own ignore rules, and `src/landing/stage.ts` additionally leaves out unignored installed or built folders (`node_modules`, `dist`, `build`, `target`, `.venv`, `venv`, `__pycache__`, `.next`, `.nuxt`, `.gradle`, caches, `coverage`) and new binary files over 5 MB, so a project without a `.gitignore` is not flooded. What was left out is recorded on the landing and named in the outcome; when a large file was left out, the Goal's folder and branch are kept so the file is not lost.
2. Choose the mode, once: a pull request when the project has a remote, `gh` is installed and signed in, and the Goal's base commit is already on the remote's branch; otherwise a local merge, with one plain sentence saying why nothing was pushed.
3. Merge the latest main branch into the Goal's branch inside its own worktree. A conflict is aborted cleanly and the Worker is resumed once (`landing.conflictFixAttempts`) with the files and the commit to merge; if it is still unresolved the Goal is Blocked. If the merge changed anything, the Brief's checks are re-run there, so the work is Verified against the merged result; a failure also goes back to the Worker once.
4. If the merge would publish something and `landing.autoMergePublishing` is off, ask the user (see below) and park the Goal in `waiting_for_user`.
5. Local: create the merge (or squash) commit from the verified tree with `git commit-tree`, then move the main branch to it. If a checkout has the branch checked out it is fast-forwarded with `git merge --ff-only` (Git itself refuses if that would overwrite the user's edits, which Blocks the Goal and changes nothing); otherwise only the branch ref is moved with a compare-and-swap `update-ref`. The user's current branch and uncommitted edits are untouched, and the outcome says so in one sentence. If main moved meanwhile the work is combined and checked again (up to three passes).
6. Pull request: push the branch (a fast-forward, never forced), look for an existing PR for the branch before creating one, poll `gh pr checks --required` with the injected clock (no model calls) for up to `landing.requireCiWaitMs` (failing checks go to the Worker once), confirm main did not move, and merge with the configured method (`merge`, or the first method the repository allows). It then fast-forwards the user's local main only when that is safe.
7. Remove the worktree and the local branch. Unverified work is never merged: it stays on its branch and the outcome names it.

**Working copies of Goals that did not land.** Cancelled, failed, Blocked, held and Unverified Goals keep their worktree and branch, so nothing is lost. `Landing.sweep` runs at startup and hourly (on the injectable clock) over every worktree whose Goal has ended. With no unsaved changes and every commit already on the main branch, the folder and branch are removed. Otherwise nothing is touched until `landing.worktreeRetentionMs` (14 days) after the Goal ended; then unsaved changes are saved as a commit on the Goal's branch (same safeguards, hooks not run), the folder is removed, and the branch stays (workspace state `archived`). A branch with commits not on the main branch is never deleted, and only `preston/...` branches whose folders are inside `<home>/worktrees` are ever touched, never the user's own branches or checkouts.

**Merging again.** A Goal that ended Verified but was held back (the user said no to a publishing question) or Blocked by landing (an overlap with the user's own edits, a pull request whose checks timed out, a conflict) is not reopened for new work; follow-ups are still new Goals. The Coordinator's `goal_land(goalId, allowPublishing?)` retries only its merge: it checks that the work was verified and not already merged, restores the folder from the branch if it was archived, clears what stopped the last landing (the fix counter, the CI clock, the old question), starts a Run that continues the Worker's Session in case landing needs it, and moves the Goal back to `verifying`. The same steps and safety rules apply, so a pull request already open is reused. Without `allowPublishing` a merge that would publish is asked about again; `allowPublishing: true` stands for that one merge and is accepted only while answering a message from the user. A second call while the merge is running returns without doing anything, and a Goal already merged is refused. Each landing outcome is a new message (the outcome dedupe key includes the Run).

**Merges that publish.** `src/landing/publishing.ts` reads repository files only as data and decides deterministically: platform files (`vercel.json`, `netlify.toml`, `render.yaml`, Fly, Heroku, Cloudflare, fastlane, release tooling), a `gh-pages` branch, and GitHub workflows that run on a push to the branch being merged into (tag-only, other-branch, pull-request-only, manual and release-triggered workflows do not count) and publish or deploy. Anything found, certain or not, gets one plain question with a recommendation through the ordinary `ask_human` path (`Questions.askHuman`); the Coordinator records the reply as `yes` or `no` with `answer_worker`, and anything unclear means no. "No" leaves the verified work on its branch (and its PR open). `landing.autoMergePublishing` in config, or the standing-order policy flag of the same name for the Goal's Project (`StandingOrders.effectivePolicy`), lifts the question: either one is enough.

Landing settings are in `config.landing`: `mergeMethod`, `autoMergePublishing`, `requireCiWaitMs`, `ciPollIntervalMs`, `ciStartGraceMs`, `conflictFixAttempts`, `worktreeRetentionMs`; the Coordinator changes them with `config_update`. Preston's own pushes and merges are Preston's decisions, not the Worker's, so the default Brief authority ("do not push") does not stop a pull request.

## Supervision, quota and recovery

All of this is deterministic and persisted; none of it calls a model.

**Run health** (`src/supervisor/stalls.ts`): `active`; `busy_tool` (quiet past the idle threshold while a tool or command is still running, which is plausible); `stalled` (a live turn silent past `supervision.idleStallMs`, default 10 min, or `supervision.toolStallMs`, default 60 min, while a tool runs); `waiting_on_input`; `quota_blocked`; `exited_unexpectedly`; `parked`; `ended`. On a stall Preston saves evidence (`transcripts/<runId>/stall-*.json` and an event), interrupts the turn and resumes the same Session once with a note. If it stalls again, or fails after that resume, it raises one Coordinator event; the Coordinator answers with `goal_change_strategy` (`retry_with_note`, `fresh_session`, `switch_agent`, `report_blocked`). If it decides nothing, or after `supervision.maxStrategyChanges` (default 2) events, the Goal ends Blocked. Ordinary unexpected exits are still recovered up to `recovery.maxAttempts`.

**Quota** (`src/quota/`): each bucket (provider window, `auth:<agent>` for a login) has a persisted state: `unknown`, `available`, `blocked`, `spend_blocked` or `auth_broken`.

- A turn that ends `quota_blocked` parks its Run on the bucket and the Goal becomes `waiting_for_quota`, never failed. `rate_limit` (and Claude's ambiguous retryable 429s) only waits `quota.rateLimitWaitMs` (1 min, doubling to 10 min) on a timer. `auth_error` makes the Goal `waiting_for_login` and tells the user once how to sign in. `spend_limit` is told to the user once; Preston never buys credits or enables paid usage.
- One monitor per bucket serves every Run and the Coordinator waiting on it. Checks use the token-free read (`readQuota`, or `detect()` for a login) every `quota.recheckIntervalMs` (12.5 min ±`jitterRatio` 20%), backed off by `backoffFactor` (1.5) up to `maxRecheckIntervalMs` (60 min), and just after an advertised reset (`resetGraceMs`), so an early reset is seen at the next check. Without a read, the check is a probe: one waiting turn is resumed, every `probeIntervalMs` (30 min, backed off); its result and cost are recorded in `quota_checks`. Spending limits are not probed unless the user says `resume`.
- When a bucket is available, waiters resume the same Session with a short note ("quota restored; continue from where you stopped; verify current state first"), one at a time, `resumeStaggerMs` (90 s) apart, stopping if the bucket blocks again.
- A wait is told to the user only when it is expected to last longer than `quota.notifyAfterMs` (30 min), once per wait. With both agents enabled and `agents.balanceByQuota`, a wait longer than `quota.switchAfterMs` (1 h) hands the Goal to the other agent if it has headroom: a new Session seeded with the Brief and a checkpoint (last report and message), told once, never claimed as exact continuation.

**Processes and side effects**: agent PIDs are recorded with a start identity (`agent_processes`) while a turn runs. On startup, any recorded process that still has the same identity is terminated before Sessions resume; a reused PID is left alone. A verification's record and the transition it causes are one transaction, and every notification has an outbox dedupe key, so a restart neither repeats a check result nor sends a message twice.

## Testing

- `npm run check` runs typecheck, lint and tests. CI (`.github/workflows/ci.yml`) runs it on macOS, Windows and Linux with Node 22 and 24, then builds and runs `npm run test:pack`, which packs the package, installs the tarball into a temporary prefix and runs the installed `preston --version`. `.gitattributes` keeps LF line endings on Windows checkouts.
- Behaviour tests start a real Preston runtime (`createRuntime` from `src/runtime.ts`, or `startDaemon` for IPC) against a temporary `PRESTON_HOME`, using the fake Channel (`src/channels/fake`) and the fake Worker adapter (`src/workers/fake`), with an injectable clock. They assert on Channel messages, Goal outcomes and files on disk. `test/support/harness.ts` wraps this.
- Landing tests (`test/landing`) use real `git` in throwaway repositories under the temp directory and a `FakeGitHub` (`test/support/github.ts`) whose remote is a real bare repository; `gh` itself is only tested for the arguments it is given. `test/support/git.ts` isolates them from the developer's own git configuration.
- Process-level tests run the real executable, which the test global setup builds into `.preston-test-dist/`.
- Agent adapters are tested against recorded CLI transcripts.
- Real-provider smoke tests live under `test/smoke/` and run only through `npm run smoke`, never in CI.
